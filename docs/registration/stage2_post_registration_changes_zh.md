# eval_v2 登记后的运行变更说明

登记版本：方案 v2.3（`实验设计方案_v2.md`），冻结记录 `FREEZE_MANIFEST_v2.json`，2026-10-28 07:50 登记，07:51 在服务器上启动。

登记之后只对“调度与启动方式”做过修改，没有改变数据、题目、候选证据池、模型、提示词、解码参数、评审规则、评分或统计分析。每次改动后第一次启动时，启动器会在 `变更记录_v2.txt` 中自动记下与登记版本不同的文件；本文件说明每次改动的原因和内容。

## 2026-10-28（第 1 次）

**起因。** 07:51 启动成功之后，08:15–08:17 三次“查看进度并下载结果”都在 ssh 握手阶段被服务器断开（`Connection closed by <SERVER> port <PORT>`），同一时间段手动登录正常。断开发生在密钥验证之前，和免密登录无关；当时流水线正在同时下载模型、把 4B 模型以 fp32 读入主机内存，服务器可能暂时资源吃紧，也可能是 sshd 对新连接暂时限流。仅凭这一行提示无法确定原因。

**改动的文件与内容。**

| 文件 | 改动 |
|---|---|
| `tools/launcher.ps1` | 连接失败时自动重试（约 2 分钟），最后一次把 ssh 的详细连接过程记入本机 `logs\` 下的记录；每次查看进度时把服务器资源情况记入同一记录（窗口里不显示） |
| `server/pipeline.py` | 1. 按主机内存调度：预计内存峰值较大的作业（把模型以 fp32 读入内存、建 BM25 索引）在可用内存不足时排队，不再与其他大作业同时加载；2. 调度程序可以在作业运行期间替换：收到退出信号时在两轮调度之间退出，新的调度程序接管正在运行的作业（状态文件里漏记的作业从进程列表找回），已完成的作业不重跑；同一时间只允许一个调度程序；3. 进度表显示服务器可用内存 |
| `server/run_v2.sh` | 代码更新后启动时只替换调度程序、不中断作业；新增 `sysinfo`（内存、内存压力、负载、内核内存不足记录、ssh 服务近期记录） |
| `运行说明.md` | 相应的使用说明 |

**对结果的影响。** 无。作业的开始时间可能因为等待内存而推迟，但每个作业的输入、代码与参数都不变；作业之间只通过已完成作业的输出文件衔接，开始时间和先后顺序不进入任何计算。

## 2026-10-29（第 2 次）

**起因。** 10 月 28 日 17:19 部署第 1 次改动、流水线续跑之后，到 10 月 29 日 10:03 查看进度时：

1. **评审 A 与 G2 被错误地换成了单卡备选模型。** 从 hf-mirror 下载 GLM-4-9B-0414 时，huggingface_hub 默认使用 Xet 存储协议，镜像站无法转发它的认证，返回 401。旧版下载程序在下载失败时改用了单卡备选模型 glm-edge-4b-chat，这不符合登记方案：方案第十四、十五节只允许在“缺少 accelerate 或不足两张 GPU”时使用单卡备选。备选模型只在 E0 评审冒烟中试评过校准集的冒烟答案；评审 A 还没有评任何正式答案，G2 还没有生成。
2. **E0 评审冒烟失败，所有评审作业因此受阻。** 加载评审 B（Hunyuan-7B-Instruct）时进程两次因 SIGBUS 退出。两位评审在同一个进程里试评，评审 A 已通过的结果也随进程一起丢失。10 月 28 日 07:51 下载作业记录的权重文件 SHA256 与 Hugging Face 公布的值一致，原因尚不清楚。
3. **外部验证打分失败。** Qwen3-Reranker-0.6B 在外部验证集的长病例上显存不足（每批 8 条），两次失败。
4. 此外，服务器在 10 月 28 日约 08:15 停止响应（流水线日志在 08:14:56 之后中断），约 17:08 重启（由服务器上常驻服务的运行时长推断），17:19 重新启动流水线后从断点继续。原因不明。
5. 负责人已在服务器的 `/home/<user>/models` 中准备了实验用模型，并说明缺少的模型可以用 ModelScope 下载到该目录。

**改动的文件与内容。**

| 文件 | 改动 |
|---|---|
| `server/fetch_models.py` | 1. 按顺序找模型，用第一份核对通过的：上次登记且已经用过的那一份 → 服务器上已有的副本（先找 `/home/<user>/models`，再找 `~/models`、ModelScope 与 Hugging Face 的缓存）→ 用 ModelScope 下载到 `/home/<user>/models` → 经 hf-mirror 下载（关闭 Xet，下载前删除旧的未完成临时文件）→ 按文件清单逐个直接下载（支持断点续传）。2. 只在登记方案规定的条件下使用单卡备选；找不到或下载失败时作业标为“需要处理”，不再改用备选。3. 逐个文件核对：把每个权重文件完整读一遍，核对 safetensors 文件头声明的长度；Hugging Face 缓存里的副本还要与镜像站给出的大小和 SHA256 一致，上次登记的副本要与上次记录的 SHA256 一致；其他来源（如 ModelScope）的副本与 Hugging Face 官方文件的 SHA256 对照，是否相同记入模型登记表。不能用的副本跳过（缓存里损坏的文件删掉后重新下载） |
| `server/config/pipeline.json` | 1. 增加模型目录 `/home/<user>/models` 和各模型在 ModelScope 上的名称（ZhipuAI/GLM-4-9B-0414、Tencent-Hunyuan/Hunyuan-7B-Instruct、Qwen/Qwen3-4B-Instruct-2507、Qwen/Qwen3-Reranker-4B），只影响到哪里找模型。2. 评审 A 与 G2（GLM-4-9B-0414）分配到两张卡时的显存预算由每卡 18 GiB 改为 20 GiB。用与服务器相同版本的 transformers（5.19.0）和 accelerate（1.15.0）按 GLM-4-9B-0414 的配置计算分卡方案：预算 18 GiB 时，按其分卡规则主卡要预留最大一层的空间，输出层（lm_head，2.3 GiB）会被放到磁盘，模型无法完整放进两张卡，评审 A 将无法加载；预算 20 GiB 时两张卡各放 17.5 GiB 权重，与方案“每卡权重约 18 GiB”一致。这一项只决定各层放在哪张卡上，不影响计算结果 |
| `server/pipeline.py` | 1. 启动时检查模型登记表：还没有逐文件核对的模型，或在规定条件之外使用了单卡备选的模型，让对应的下载作业重新运行。2. 作业进程启用 Python faulthandler，因 SIGBUS 等信号退出时把调用栈写进作业日志。3. 进度表在“说明”栏注明没有实际运行的作业（例如评审 B 不可用时） |
| `server/judge.py` | E0 评审冒烟中，每位本地评审在单独的子进程里加载和试评：一位评审的进程异常退出，只记为这一位评审不可用，不影响另一位。提示词、判定规程、评审模型与解码参数不变 |
| `server/score_v2.py` | 打分时显存不足，就把批量减半重试，实际批量记入运行记录。批量只影响浮点舍入，eval_v1 已规定它不计入设置指纹 |
| `运行说明.md` | 相应的使用说明 |

**对结果的影响。**

- 评审 A 与 G2 恢复为登记的 GLM-4-9B-0414。E0 中用 glm-edge-4b-chat 得到的试评结果按模型分开保存，后续作业不会使用。
- 模型来源改为 ModelScope 不改变模型本身。每份权重文件的 SHA256、来源目录以及是否与 Hugging Face 官方文件逐字节相同，都记入模型登记表（`runs/models/registry.json`），论文中据此报告。G1（Qwen3-4B-Instruct-2507）与 Qwen3-Reranker-4B 已用于已完成的生成和打分，只要原文件核对通过就继续使用原文件，保证前后一致。
- 已完成的 E1、E3 结果不受影响；其余作业的输入、代码与参数不变。
- 评审 B 如果在 E0 中仍然不可用，就按登记时代码已有的规定只用评审 A（judge.py：“评审 B 不可用时只记录原因，不影响主实验”）。这时 A–B 一致性与评审 B 敏感性分析缺失，属于次要分析，论文中如实报告。
