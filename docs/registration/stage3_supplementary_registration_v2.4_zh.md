## 一、登记时点与性质（如实说明）

本补充登记写于 eval_v2 全部结果已知之后：负责人与分析者已看过封存集和外部集的全部答案层、检索层结果。因此，本补充分析：

- 属于**结果已知后、运行之前预先写定**的补充分析，不是确认性检验；
- 结论在论文中写作“补充分析”，与原登记的主分析分开报告；
- 下文的比较、指标、统计方法和解读规则在运行前写定，运行后不再改动。

## 二、为什么要做

eval_v2 完成后的核查发现两个问题（见 `评测结果报告_v2.md` 第二节“关于评分指标”）：

1. **主指标依赖 9B 评审，且评审偏宽松。** 在抽查的 36 条“判为命中、但要点原文未逐字出现”的判定中，约一半不应判命中；评审 A 从未使用“矛盾”标签。检索条件之间的比较（H3）受影响较小，但“检索条件远低于闭卷”这一发现的幅度可能被高估。
2. **要点召回率只看答没答到。** 写错、多写不扣分，也不评价辨证论治的其他环节。

本补充分析用两种独立的方法复核，并增加一项新的比较（S4）：

- **S1、S2：** 用外部数据集 TCM-BEST4SDT 自带的专家金标和官方评测代码评分。其中 S1 是不依赖任何评审模型的客观选择题计分，S2 是官方的完整评分（含官方评审与奖励模型）。
- **S3：** 用更大的开源模型 Qwen3-32B，按原登记的评审规程重评 eval_v2 已有的全部答案。
- **S4：** 用同一份 stage4 训练数据的支持标签与相关性标签，分别微调 Qwen3-Reranker-0.6B 与 4B，与原始权重比较（第六节）。

## 三、S1、S2：TCM-BEST4SDT 官方评测

### 3.1 数据

- **来源：** TCM-BEST4SDT 辨证论治任务 `TCM_SDT.json`，300 例；GitHub 仓库 DYJG-research/TCM-BEST4SDT，提交 60407f2，文件 SHA256 d94711ac…（与 eval_v2 外部验证所用文件相同），CC BY 4.0。
- **金标：** 每例的选择题选项与答案由中医专家标注，经标注者交叉验证与第三方评议审定（数据集作者的说明）。本研究不做任何修改。
- **病例编号对应：** 病例编号 n 对应 eval_v2 外部集题号 EX{n:03d}；300 例的病例文本与 eval_v2 外部集逐字相同（已核对）。

### 3.2 条件

与 eval_v2 外部验证的 13 次运行完全对应，证据沿用 eval_v2 已经冻结的选择结果（`data/selections_external/`），不重新打分或选择：

| 组 | 运行 | 证据 |
|---|---|---|
| X00 | 1 | 无（闭卷） |
| X01 | 1 | BM25 Top-2 |
| X02 | 3（抽样 r1–r3） | 随机 2 条 |
| X04 | 3（种子 42、2026、3407） | Relevance-CE（B 编码）Top-2 |
| X05 | 3（种子 42、2026、3407） | Support-CE（B 编码）Top-2 |
| X08 | 1 | bge-reranker-v2-m3 Top-2 |
| X09 | 1 | Qwen3-Reranker-0.6B Top-2 |

种子与随机抽样先在题内平均；同一组各次运行都有结果的病例才纳入该组。

### 3.3 评测流程

- **代码：** 官方评测代码原样收录在 `official/`（Apache-2.0，未改动）。每个“条件 × 病例”调用一次官方的 `TCMBenchmark._evaluate_single_case`，即官方对单个病例的完整评测流程：
  - 证型、病性、病位、治则治法 4 个维度的选择题：每题 3 轮，第 1 轮原序，第 2、3 轮打乱选项顺序；
  - 病因、病机：由评审模型对照标准答案打分；
  - 处方：奖励模型评估方证契合度，评审模型评估配伍规律、配伍禁忌、药材安全性、妊娠禁忌；
  - 煎服方法、注意事项、随症加减：由评审模型打分。
- **被测模型：** Qwen3-4B-Instruct-2507，即 eval_v2 的问答模型 G1，由 vLLM 以 bfloat16 提供服务。
  - 解码参数用官方代码传入的值（温度 0，最多 4096 个词元）。
  - 该模型没有思考模式，按官方选项 `skip_think` 跳过 CoT 两个维度。
- **证据的加入方式（唯一的改动）：**
  - X00 的提示词与官方完全相同。
  - 其余条件在被测模型的**每一次**生成请求最前面加入以下证据段（`config/prompts_sup.json`）。证据条目的文本与 eval_v2 生成答案时相同。

    ```
    【参考证据】以下证据由检索系统从医案与中医文献中自动选出，可能与本病例相符，也可能无关或条件不符。请结合病例自行判断，可参考其中与本病例相符的内容。

    【证据 E1】
    ……
    【证据 E2】
    ……

    【任务】
    （官方提示词原文）
    ```
  - 官方任务要求必须作答（选择题、开具处方），所以这里采用“证据 + 自身知识”的作答方式，相当于 eval_v2 的 P-alt，而不是只依据证据作答的 P-main。论文中须写明这一点。
- **官方评审与奖励模型：**
  - 评审为 Qwen3-32B，奖励模型为 FangZheng-RM（基于 Qwen3-14B，ModelScope：DYJGresearch/FangZheng-RM），均以 bfloat16 由 vLLM 提供服务。
  - 请求内容与参数由官方代码决定，本研究不改动。
  - 官方代码没有指定评审是否使用思考模式，这里用 vLLM 的默认设置（Qwen3 默认开启思考），并开启 qwen3 推理内容解析器，使返回的正文不含思考过程。
- **选择题选项随机化的种子：** 42（官方评测器的默认值）。
- **失败处理：**
  - 官方代码在调用失败时把该维度记 0 分。这里把含“评测失败”的结果视为未完成，同一病例最多重试 3 次。
  - 仍失败的按官方规则保留 0 分并标记，汇总时报告数量，并做剔除这些结果后的敏感性分析。
- **审计：**
  - 记录所有评审、奖励模型与被测模型的返回内容。
  - 汇总时报告以下数量：被测模型输出达到长度上限的次数，评审或奖励模型返回中找不到 JSON 的次数（官方代码此时按默认 50 分计），选择题回答无法解析的轮次。

### 3.4 指标

- **S1（本补充分析的主指标）：** 官方选择题均分，即证型、病性、病位、治则治法 4 个维度官方得分的平均。不依赖任何评审模型或奖励模型。计分方式为官方规则：
  - 单选题（病性）3 轮全对才得分；
  - 不定项题（证型、病位、治则治法）按 S = |A∩B| / (|A| + |Ā∩B|) 取 3 轮平均，选错会扣分。
- **S2（次要）：** 官方 SDT 总分，即官方 14 个维度（skip_think 时）的平均，计算方式与官方 `_calculate_final_scores` 相同。
- **描述性：** 各维度均分。

## 四、S3：Qwen3-32B 重评要点召回

- **对象：** eval_v2 已生成的全部答案，共 18,290 条：
  - 封存集 G1 与 G2 的全部条件 14,390 条；
  - 外部集 3,900 条。
- **评审：** Qwen3-32B，bfloat16，非思考模式（与 eval_v2 评审 A、B 的非思考设置一致），温度 0，最多 2048 个词元。
- **规程与原登记完全相同：**
  - 评审提示词为 `judge_prompts.json` v2.1，未改动；
  - 要点顺序按答案编号固定打乱，与原评审相同；
  - 输出检查与重写最多 3 次；
  - 引用核对失败的“命中/部分”按“未提及”计；
  - 整体拒答记 0。
  - 代码中的这些函数逐行照搬自 eval_v2 的 `server/judge.py`。
- **不使用、也不上传证据支持标签。** 封存集的题目与参考要点会出现在租用的服务器上；它们自 eval_v1 起已在本研究的 GPU 服务器上，不含证据支持标签。

统计方法与原方案 4.4 节相同：

- 按病例（题）配对 bootstrap 10,000 次，种子 20261026，取 95% 百分位 CI；
- 族内 Holm 校正；
- 等效检验用 90% CI 与 ±0.05 比较。

| 编号 | 指标 | 比较 | 判定 | 地位 |
|---|---|---|---|---|
| S1-H3 | S1 选择题均分 | X05 − X04 | 95% CI 下界 > 0 | 本补充分析的主比较 |
| S1-H4 | 同上 | X05 − X01、X05 − X02、X05 − X00 | Holm 校正后 p < 0.05，双侧 | 次要 |
| S1-H7 | 同上 | X05 − X08、X05 − X09 | 90% CI 落在 ±0.05 之内 | 次要 |
| S2 | 官方 SDT 总分 | 同 S1 的三组比较 | 同上 | 次要 |
| S3 | Qwen3-32B 评审的要点召回率 | 重做原方案的 H3、H4（族 B）、H7，以及外部集的 HX3、HX4、HX7 | 与原方案相同 | 敏感性分析 |
| S3-κ | 评审一致性 | 评审 A 与 Qwen3-32B、评审 B 与 Qwen3-32B | 报告 κ 与一致率 | 描述 |

**事先写定的解读：**

| 结果 | 解读 |
|---|---|
| S1-H3 成立 | 支持标签的优势在专家金标、官方客观计分、“证据 + 自身知识”作答方式下同样成立，可写入摘要 |

| S3 给出的闭卷差距明显小于评审 A | 论文以 32B 的结果和人工抽查校准后的数值报告差距大小，评审 A 的数值作为原登记结果并列报告 |

## 六、S4：用支持标签微调 Qwen3-Reranker（0.6B、4B），与原始权重比较

### 6.1 为什么做

1. **回答“支持标签能否让最强的重排模型更好”。**
   - eval_v2 中最强的零样本重排模型是 Qwen3-Reranker：外部集上比 Support-CE 高 0.089。
   - 现有证据只来自 bge（E2，H2b）：支持标签微调后检索层没有超过零样本（−0.002），答案层 +0.042（p = 0.055），结论不明确。
   - 这是审稿人最可能追问的问题，也决定论文能否主张“支持标签是可以加到现有强模型上的监督信号”。
2. **把“标签”和“规模”的作用分开。** 同一家族的两种规模（6 亿、40 亿参数），用同一份数据、同一流程、同一标签训练。参数量之外的条件全部相同，可以直接回答“参数量差异是否影响结果”。
3. **在第三个骨干上复现标签效应（支持对相关性）。** E1、E2 已在 mDeBERTa 与 bge 上观察到。

### 6.2 训练（`sup/s4_train.py`）

- **数据：**
  - 与 stage4、E2 完全相同的 `prepared.pt`：平衡训练集 26,432 对，以及相同的 dev、test 切分；
  - 标签为 `y_support`（支持）或 `y_relevance`（相关性）；
  - 由本机“导出S4训练数据.bat”从 P40 服务器只读导出，导出包内含文件 SHA256 清单。
- **模型：** Qwen/Qwen3-Reranker-0.6B 与 Qwen/Qwen3-Reranker-4B 的官方权重（ModelScope），与 eval_v2 的 G09、G13 相同。
- **输入格式：** 与 eval_v1、eval_v2 零样本打分完全相同（官方提示格式与同一句中医任务说明）。训练目标为最后位置上“yes / no”两个词元的二分类交叉熵，与模型的打分方式一致。
- **方法：**
  - LoRA：r = 32，alpha = 64，dropout 0.05，作用于注意力与 MLP 的全部线性层；
  - 学习率 1e-4，warmup 10% 后线性衰减，weight decay 0.01；
  - 有效批量 16（4 × 4 累积），最多 3 轮；
  - 梯度裁剪 1.0，梯度检查点，bf16；
  - 训练输入最长 1024 个词元。
- **检查点选择与 E2 相同：** 每轮在 dev 上用 stage4 的 `checkpoint_key` 选择，连续 2 轮不提升即停止；dev 定阈值后，在 test 上报告支持类的 P、R、F1。
- **运行：** 2 种规模 × 2 种标签 × 3 个种子（42、2026、3407），共 12 次。超参数不在任何评测集上调整。

### 6.3 打分与选证据

- **打分：** 14 个模型（2 个原始权重、12 个微调后）给封存集（3,520 对）与外部集（6,000 对）的候选池打分。
  - 打分方法与 eval_v1 的 `score_qwen3` 相同：log P(yes)，最长 2048 词元；
  - 精度统一为 bf16。原始权重也在这里重新打分，保证与微调模型可比。
- **选证据：** 每题取 Top-2，规则与 eval_v2 相同：分数从高到低，同分按检索名次。

### 6.4 生成答案与评分

- **新条件**（每个数据集 14 次运行），简称 Q06 = 0.6B，Q4B = 4B：

  | 简称 | 含义 | 运行次数 |
  |---|---|---|
  | Q06N、Q4BN | 原始权重 | 各 1 |
  | Q06S、Q4BS | 支持标签微调 | 各 3 个种子 |
  | Q06R、Q4BR | 相关性标签微调 | 各 3 个种子 |

- **参照条件：** 闭卷（G00、X00）、Relevance-CE（G04、X04）、Support-CE（G05、X05）。沿用 eval_v2 冻结的证据选择，在云端重新生成答案，使所有条件的生成环境相同。
- **生成：** Qwen3-4B-Instruct-2507，vLLM，bf16。提示词为 eval_v2 主提示词 P-main（只依据证据作答），与 eval_v2 的 `generate.py` 逐字相同；贪心解码，最多 768 个词元。
- **评分：**
  - 要点召回：封存集与外部集，用 Qwen3-32B 按原评审规程评审，同第四节；
  - 外部集另做官方选择题评测：同 S1 的流程与证据段，只做选择题部分。参照条件的选择题得分取自 S1；
  - 封存集上的检索层指标（严格、分级覆盖率等）用证据金标在本地计算，不在服务器上进行。

### 6.5 比较与判定（运行前写定）

统计方法同第五节。种子先在题内平均。

| 编号 | 比较 | 指标与数据 | 判定 | 地位 |
|---|---|---|---|---|
| S4-H1 | Q06S − Q06N；Q4BS − Q4BN | 外部集要点召回（Qwen3-32B） | 两项一起 Holm 校正，p < 0.05 且差值 > 0 | **S4 主比较** |
| S4-H1′ | 同上 | 封存集要点召回；外部集官方选择题均分；封存集检索层严格与分级覆盖率 | 同上 | 次要（复现） |
| S4-H2 | Q06S − Q06R；Q4BS − Q4BR | 同 S4-H1 的各指标 | Holm 校正，p < 0.05 | 次要 |
| S4-H3 | Q4BS − Q06S；Q4BN − Q06N；Q4BR − Q06R；交互项 (Q4BS − Q4BN) − (Q06S − Q06N) | 同上 | 报告差值与 95% CI | 描述（规模） |
| S4-H4 | Q06S − Support-CE；Q4BS − Support-CE | 同上 | Holm 校正，双侧 | 次要 |
| — | stage4 test 上支持类的 P、R、F1 | 12 个微调模型 | 报告 | 描述 |

**事先写定的解读：**

| 结果 | 解读 |
|---|---|
| S4-H1 对某一规模成立 | 支持标签能在该规模的最强零样本重排模型上带来额外收益，可作为论文的主要贡献之一 |
| S4-H1 两种规模都不成立，但 S4-H2 成立 | 支持标签优于相关性标签，但不能超过强模型原有的相关性训练。论文贡献限定为“标签定义的比较”，不主张对强模型有增益 |
| S4-H3 中规模差值小、置信区间含 0 | 在本研究的候选池与题量下，参数量不是主要因素 |
| S4-H4 中 Q4BS 显著优于 Support-CE | 论文中 EEE 层可换用支持标签微调的 Qwen3-Reranker，并如实说明计算代价 |

### 6.6 S4 特有的偏离与限制

- **训练方法与 E2 不同：** 这里用 LoRA，E2 对 bge 用全参数微调。原因是两种规模要用同一方法，而 40 亿参数的全参数微调显存开销过大。论文中如实说明。
- **超参数沿用常见设置：** 学习率等用 LoRA 的常见设置，未调参。如果效果不佳，不能排除调参后会更好。
- **生成环境：** 参照条件在云端重新生成（bf16），与 eval_v2 的 P40 fp32 答案不直接比较。S4 只比较本次运行内部各条件之间的差。

## 七、已知的偏离与限制

- **生成精度不同：** S1、S2 中被测模型在 vLLM 上以 bfloat16 运行，eval_v2 在 P40 上以 fp32 运行。S1、S2 只比较本次运行内部各条件之间的差，不与 eval_v2 的答案直接比较。
- **结果不完全可复现：** vLLM 的批处理使贪心解码在不同批次组合下可能有极小差异，重跑结果可能略有不同；服务中断后重启、改用备用部署或备用启动方式（第八节）也属此类。全部输出与实际部署都保存。
- **评审的思考模式：** 官方评审的思考模式在官方材料中没有说明，这里采用默认（开启）。如有影响，论文中说明。
- **官方代码的默认分：** 官方代码在评审或奖励模型输出无法解析时按默认分计（多为 50 分）。按 3.3 节审计报告次数，不做更正。
- **证据选择沿用 eval_v2：** 外部集的候选池与证据选择均来自 eval_v2，已在登记时冻结。
- **原有限制不变：** 封存集的参考要点仍由 AI 代理标注。方案 4.3 节的人工抽查另行进行，不在本补充分析范围内。

## 八、执行与资源

### 8.1 硬件（运行前修订：2026-11-04）

- **实际租用：** 2 张 Blackwell 架构工作站卡，RTX PRO 6000（96 GB）或 RTX 6000D（84 GB），PCIe、无 NVLink；数据盘 ≥ 300 GB；驱动 ≥ 570（CUDA 12.8）。
- **为什么够用：** 三个服务模型的 bf16 权重合计约 97 GB（Qwen3-32B 约 61 GiB、FangZheng-RM 约 28 GiB、Qwen3-4B 约 7.5 GiB），两张卡合计 168–192 GB。S4 微调每张卡同时只跑一个作业，4B 的 LoRA 微调峰值显存远低于 84 GB。
- **显卡分配（`config/sup.json` 的 serve 段，`sup/serve.py`）：**

  | 阶段 | 0 号卡 | 1 号卡 |
  |---|---|---|
  | S1/S2 官方评测、S4 生成答案与选择题（all 模式） | 评审 Qwen3-32B（显存比例 0.92） | 奖励模型（0.50）+ 被测模型（0.40） |
  | S3 重评、S4 答案评审（judge 模式） | 评审，两卡张量并行（0.92）；不行则两卡各一个评审副本 | 同左 |
  | S4 微调与打分 | 一个作业 | 一个作业 |

  评审独占一张卡，是为了给它留出足够的 KV 缓存（84 GB 卡上约 10 GiB 以上，可容纳 4 万个词元以上）。只开评审的阶段改为两卡并行或两个副本，以加快 S3。
- **启动方式：** 每个服务依次尝试 default → eager（`--enforce-eager`，不用 CUDA graph）→ triton（另设 `VLLM_ATTENTION_BACKEND=TRITON_ATTN`），直到就绪并通过一次问答核对。两卡并行一律加 `--disable-custom-all-reduce`（PCIe 卡只用 NCCL）。实际用到的部署与方式记入 `logs/servers_history.jsonl`，并写进汇总的“运行环境”一节。
- **对结果的影响：** 张量并行与否、副本数、是否用 CUDA graph、注意力实现，都不改变模型、提示词和解码参数，只可能带来浮点舍入层面的差异。这与第七节“结果不完全可复现”同属一类，论文中一并说明。
- **原方案中的 4 卡方案（4 张 ≥44 GB）** 仍保留在代码中，不再是推荐配置。

### 8.2 运行顺序：先验证、后长跑

为避免在租用的机器上反复失败，全部检查与试跑排在长时间运行之前。任何一项不通过，程序立即停下并说明原因。

1. **环境：**
   - 检查驱动与磁盘；
   - 缺少 C 编译器或 Python 头文件时自动安装（Triton 编译内核需要）；
   - 建立独立的 Python 环境，安装固定版本；
   - pip、编译与内核缓存全部放到数据盘。
2. **显卡预检（下载大模型之前，约 2 分钟，`sup/preflight.py gpu`）：**
   - 分配方案；
   - PyTorch 对本卡架构（sm_120）的支持；
   - 每张卡的 bf16 矩阵乘与注意力数值；
   - Triton 内核编译、torch.compile；
   - 双卡 NCCL 通信，不通时改试 `NCCL_P2P_DISABLE=1` 并记下；
   - vLLM 导入；
   - 磁盘、共享内存、内存。
3. **vLLM 预检（先只下载 8 GB 的被测模型，`sup/preflight.py vllm`）：** 用被测模型实际启动 vLLM，检查三种部署：
   - 单卡；
   - 同卡两个服务（显存比例与正式部署相同）；
   - 两卡张量并行。

   同时确定每种部署可用的启动方式，并预热内核编译缓存。
4. 下载其余模型，校验分片是否齐全，记录 SHA256；核对 S4 训练数据。
5. **试跑：**
   - 三个服务的接口检查（`preflight.py api all`）：
     - 评审在思考模式下返回 JSON，正文不含 `<think>`；流式返回同样检查；
     - 评审在非思考模式下返回 JSON；
     - 奖励模型按官方方证匹配提示词返回“匹配分数”；
     - 被测模型正常作答。
   - 官方评测试跑（3 例 × 2 个条件）。验收标准：全部成功；评审输出缺 JSON 或被截断合计不超过 1 次；奖励模型同样不超过 1 次；被测模型截断不超过三分之一。
   - S4 生成试跑：8 条，用参照条件的冻结证据。
   - 评审单独服务的接口检查。
   - S3、S4 重评试跑，各 6 条；有效不少于 5 条。
   - S4 微调冒烟测试：0.6B 与 4B 各训练 15 步并试打分，给出全部微调的用时估计。
6. **正式运行：**
   - S4 的 12 次微调、打分、选证据；
   - S1/S2；
   - S4 生成答案与选择题评测；
   - S3 重评；
   - S4 答案评审；
   - 汇总并打包。

### 8.3 运行中的故障处理

- **服务中断：** 某条任务失败时先检查服务健康（相隔 20 秒查 3 次）。服务已中断时：
  - 这次失败不计入该病例或答案的重试次数，不会把服务故障记成 0 分；
  - 程序以退出码 3 结束，自动停止并重启服务，从断点继续，同一步骤最多重启 3 次。
- **官方代码吞掉的调用失败：** 官方代码会捕获部分调用异常并继续评分（例如用空回答）。因此，同一病例中只要有一次调用在重试后仍失败，整例就视为未完成：服务已中断的按上一条处理，否则计一次重试。这样服务故障不会悄悄变成低分。
- **服务卡死：** 连续 30 分钟没有任何任务完成，视为卡死，按服务中断处理。
- **断点续跑：** 结果逐条追加写入，已完成的不重跑。重启机器后再运行一次 `bash run_all.sh` 即从断点继续。
- **启动方式的记忆：** 某个服务一旦以某种方式启动成功，之后重启时优先用该方式。
