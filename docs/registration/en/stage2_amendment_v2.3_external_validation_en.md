## Part 2. Section 16 (new in v2.3)

## 16. v2.3 revision (before registration): external validation (E8, TCM-BEST4SDT)

### 16.1 Purpose

The reference labels of the sealed set were annotated and adjudicated by AI agents (Section 13), and the set was already used once in eval_v1. To test whether the main answer-level conclusions depend on this dataset, the comparisons of H3, H4 and H7 are repeated on an independent public dataset annotated by TCM experts, with exactly the same retrieval corpus, rerankers, QA model, prompts and judging protocol. The analyses of the external validation and of the sealed set are fixed together at registration, launched once and run automatically.

### 16.2 Data

- **Source:** the syndrome-differentiation and treatment task of TCM-BEST4SDT (`TCM_SDT.json`, 300 cases; taken from GitHub repository commit 60407f2, file SHA256 d94711ac…; the dataset is formally archived on Figshare, DOI 10.6084/m9.figshare.30615956). The cases come from clinical case records and famous physicians' case records; the standard answers were annotated by TCM experts, cross-validated by the annotators and approved by a third-party review committee. The data are released under CC BY 4.0. Citation: Li K, et al. arXiv:2512.02816, 2025.
- **Case types (pre-specified strata):** IDs 1–150 are adapted famous physicians' case records and textbook-style cases (classical); 151–300 are modern clinical cases (modern; of these, 151–199 are outpatient records with visit dates).
- **Relation to the other data of this study:** the dataset is not used for any training, tuning or protocol development in this study; cases that are near-duplicates of CE training cases are excluded on the server (16.4).

### 16.3 Questions and reference points (`analysis/build_external_set.py`, run before registration; outputs uploaded with the code and hash-frozen)

- **One question per case.** The question type is assigned deterministically by the parity of sha256("EXT-QTYPE:"+ID): 148 diagnosis questions and 152 treatment-principle questions. Question = the original case text (only leading and trailing whitespace removed) + the question-type instruction, identical word for word to the sealed set.
- **All reference points are taken from the expert standard answers, extracted by deterministic rules, without human or AI editing:**
  - Diagnosis questions: disease diagnosis (the "TCM disease diagnosis" field, with the syndrome pattern or Western disease name in brackets removed) + syndrome elements (the "syndrome pattern" field split, at most 3) + pathogenesis (the first 2 qualifying clauses of the "pathogenesis" field: 4–12 characters, containing pathogenesis terms, not connectives or symptom descriptions);
  - Treatment-principle questions: treatment principles (the "treatment principle and method" field split).
  - 958 points in total (disease diagnosis 151, syndrome pattern 190, pathogenesis 273, treatment principle 344); on average 4.1 per diagnosis question (sealed set 3.9) and 2.3 per treatment-principle question (sealed set 2.2); median point length 4 characters.
  - One obvious typing error is corrected by a lookup table (case 168: "白庁" → "白疕" [psoriasis]).
- **Hinting phrases in the question.** The case text is not changed. In 54 questions the text contains clauses that may hint at the answer (e.g., "showing that there is a heat pattern in the body"); they are flagged by the same rule as for the sealed set (`leak_fragments`) and used only for reporting and sensitivity analysis, not for exclusion.

### 16.4 Processing on the server (`server/build_external.py`, job ext_build; text processing only, no model is run)

1. **Near-duplicate exclusion (same rule as for selecting the sealed questions).** Cases with a character 2–3-gram TF-IDF cosine ≥ 0.85 to a CE training case (stage4 training set) are not included; among near-duplicates within the external set, the one with the smaller ID is kept. The TF-IDF implementation is equivalent item by item to the sklearn settings (verified; cosine difference < 10⁻¹³).
2. **Candidate pools (exactly as for the sealed set).** The same retrieval corpus (about 1.82 million entries), character-bigram BM25 (k1 = 1.2, b = 0.75), retrieval with the question text only, top 20, title plus 160 characters of context on either side. The implementation matches `scripts/server_build_pools.py` bit for bit (checked item by item on a test corpus, including the BM25 scores).
3. **Exclusion of the case's own original record.** For the sealed set, the case's own snippets are excluded by record ID; external cases have no ID in the corpus, so the judgement is made from the text. A candidate is excluded, and the next ranks move up, if any of the following holds:
   - a. the proportion of the case text's character bigrams contained in the candidate is ≥ 0.6 (computed with the same implementation; over the 3,520 sealed-set candidates this proportion has median 0.17, 99th percentile 0.35, maximum 0.44);
   - b. the candidate contains ≥ 60% of the herb names in the prescription (prescription of at least 4 herbs) and the above proportion is ≥ 0.2 (to recognise the original text of the same case record without excluding normal evidence that only discusses prescriptions);
   - c. the candidate contains verbatim one clause of ≥ 10 characters, or two or more clauses of ≥ 6 characters, from the "aetiology" or "pathogenesis" of the standard answer.

   The three indicators of every detected candidate are written to `pool_filter_log.jsonl`, and the numbers excluded are summarised by rule in `EXT_MANIFEST.json`.
4. The outputs are generated only once and their hashes recorded in `EXT_MANIFEST.json`; they are checked at every later read, and the pipeline stops if a file has been changed.

### 16.5 Conditions (k = 2, P-main, G1; settings identical to the sealed-set conditions with the same numbers)

| ID | Corresponding sealed-set condition | Evidence | Runs |
|---|---|---|---|
| X00 | G00 | Closed-book | 1 |
| X01 | G01 | BM25 Top-2 | 1 |
| X02 | G02 | 2 random passages (seeds 101, 202, 303) | 3 |
| X04 | G04 | Relevance-CE (B encoding) Top-2 | 3 (seeds) |
| X05 | G05 | Support-CE (B encoding) Top-2 | 3 (seeds) |
| X08 | G08 | bge-reranker-v2-m3 (full input, eval_v1 setting) | 1 |
| X09 | G09 | Qwen3-Reranker-0.6B (full input, eval_v1 setting) | 1 |

- 13 runs and about 3,900 answers in total. Seeds and random draws are first averaged within each question (as in 4.4).
- Same scoring safeguards as for the sealed set: the CE B-encoding setting must already have passed on the calibration set; for bge and Qwen3-Reranker, the full-input setting is first recomputed on the calibration set and checked against the eval_v1 calibration scores (maximum difference ≤ 10⁻³), and only then is the external set scored.
- **Long cases.** 26 external questions are longer than 500 characters (the longest sealed question has 279). The CE B encoding has a total length of 512 and does not truncate the question, so for very long cases few or no tokens are left for the evidence, and X04 and X05 then effectively approach the BM25 order. The settings are not changed (same as G04 and G05). The number of question and evidence tokens actually fed in is recorded for every question, and a sensitivity analysis is specified in advance: recompute HX3, HX4 and HX7 keeping only questions whose CE input contains at least 64 evidence tokens.

### 16.6 Judging, metrics and hypotheses

- **Judging:** same protocol as for the sealed set (Appendix B). Judge A judges all answers; judge B judges all conditions for the questions with sha256("B:"+ID) mod 4 = 0 (about 25%). The external set has no evidence-support labels, so only key-point recall is judged, not claim faithfulness.
- **Primary metric:** strict key-point recall (KPR); the unit of analysis is the question (the included cases, expected to be about 300).
- **Pre-registered comparisons (family G, see 4.4):**
  - HX3: X05 − X04, lower bound of the 95% CI > 0 (tested alone);
  - HX4: X05 − X01, X05 − X02, X05 − X00, Holm-corrected, p < 0.05 (two-sided against X00);
  - HX7: X05 − X08 and X05 − X09, 90% CI within ±0.05.
- **Strata and sensitivity:** case type (classical, modern) and question type (diagnosis, treatment principle) are descriptive strata. Sensitivity analyses: drop the questions with hinting phrases; keep only the questions whose CE input has at least 64 evidence tokens (16.5); recompute on judge B's subset with A's labels, B's labels and the lower of the two. A–B agreement (κ) is also reported.
- **Power:** with about 300 questions and an SD of the paired difference of 0.20–0.25, the minimum detectable difference at 80% power is about 0.032–0.040, slightly better than for the sealed set (Section 4.5).
- **Interpretation:** see the three new rows in Section 7. The external results are reported as an external replication and do not replace the primary hypothesis H3 on the sealed set.

### 16.8 An incomplete launch under v2.2, and problems fixed at the same time

**The v2.2 launch of 2026-10-27.** That evening the pipeline was launched twice under v2.2 (local launch records: 22:43 and 22:52; registration confirmed at 22:47). The server could not see its GPUs at the time (nvidia-smi reported "Failed to initialize NVML"), and the pipeline marked all GPU jobs as "blocked" (GPU required, 0 available), so no scoring or generation took place on the sealed set. v2.3 is frozen and registered again; the freeze and registration records of v2.2 are moved to the local `logs/registration_v2.2_…/`, and the run directory left on the server by that launch is renamed as a whole to `runs_before_v2.3_…` and kept for checking.

[Translator's note: "registered again" reflects the intention at the time. The v2.3 files were frozen, but they were not deposited on OSF.]

**Fixed at the same time:**

- **Quoting in the launcher.** PowerShell 5.1 does not escape double quotes in arguments when calling ssh, so the original `sed -i "s/\r$//"` was executed on the server as `s/r$//`, deleting the letter r at the end of lines of run_v2.sh (which is why `--format=csv,noheader` of nvidia-smi reported "Format modifier is not recognized"). Remote commands now use single quotes only.
- **Environment check at every launch.** Previously, once the environment check had completed it was not repeated, so the result "0 cards" would be kept even after the GPU problem was fixed. Now the check is redone at every launch of the pipeline; if no GPU is available, the jobs are marked "needs attention", and the progress table states the reason and what to do. The final summary is also regenerated after every launch.
- **Run state by protocol version.** The launcher records the protocol version (v2.3). If the existing local registration record belongs to an older version, it is archived automatically and registration is repeated; if the run directory on the server is not of the current version, it is renamed as a whole and kept, and the run starts from a clean state; with the same version, the run resumes as usual.
- **Concurrent writes to the scoring records.** Several scoring jobs for the same target set may run at the same time (e.g., CE scoring and public-model scoring on the calibration set). Previously each wrote the whole of `RUN_MANIFEST.json`, so a later write overwrote earlier records; now a file lock is used and each job merges only its own records.
